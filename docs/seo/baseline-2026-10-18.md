# Baseline of numaliving.us, 18 October 2026

What the live site looked like before any SEO work: the served HTML and the cold mobile speed. The numbers are the reference for every later phase, so each can be measured again the same way (see the end of this page). The competitors and the search results are in [`competitor-analysis-2026-10.md`](competitor-analysis-2026-10.md).

## 1. The served HTML

- All 14 URLs carry `noindex` (intended). Canonical: 0 of 14. Open Graph and Twitter tags: 0. JSON-LD: 0. `sitemap.xml`: 404. `robots.txt` has no `Sitemap:` line. `<html lang="en">`.
- 8 URLs share one meta description. Titles are brand-first and generic ("Process | Numa Living", 21 characters).
- Main-content words per page:

  | Page | Words |
  | --- | --- |
  | home | 295 |
  | capabilities | 290 |
  | about | 211 |
  | projects | 200 |
  | process | 194 |
  | contact | 153 |
  | a project page | 130 |
  | login | 70 |

  `/process/`, `/contact/` and `/projects/` have no H2.
- Images: 30 JPEGs, 15 MB, up to 1.07 MB each, sampled files 1600x1067. No WebP or AVIF, no `srcset`, no width and height. Every gallery photo's alt text is the project name. File names are `DSC00614.JPG`, `Marina-View-0001.jpg`, `condor-golf-links18-photo-by-intelier-01.jpg`.
- `/index.html` answers 200 as a duplicate of `/` with no canonical. Redirects are clean 301s: http to https, www to apex, `/about` to `/about/`, old Pages URL to the apex. GitHub Pages sends `cache-control: max-age=600` and no HSTS.
- No analytics and no Search Console verification in the HTML.
- Content: the hero lists "Australia · India · Qatar · UAE · UK · USA" with Australia first; the typo "Austalia & Asia"; sample figures (120+ projects, 14 countries, 18,000 m², 250 staff); 6 sample projects in UAE, UK and India, none in the US; placeholder phone and address; certifications "to be confirmed"; a client portal promoted but not built; the quote form's location placeholder is "e.g. Dubai, UAE". The 18 October summary says the form cannot deliver until `FORMSUBMIT_ID` is set: re-verify.

An early prototype of the page analysis also listed Google Analytics 4 for these pages. That was a false positive (the signature ran case-insensitively over the whole page and matched class names and ordinary text); it is fixed in `tools/seo/html_facts.py` and covered by regression tests.

## 2. Speed, cold on a phone

Chrome DevTools, mobile 390 px wide, Slow 4G, 4x CPU slowdown, cold cache. These are lab numbers, not field data.

| Page | LCP | CLS | Notes |
| --- | --- | --- | --- |
| Home | 2.35 s | 0.00 | text LCP, 233 kB re-downloaded for lack of a long cache |
| `/projects/golf-links/` | **29.5 s** | 0.00 | LCP image took 28.8 s; 8.16 MB of images across 15; Chrome estimates 6.5 MB avoidable |

Image bytes per page: projects 1.75 MB, marina-villa 4.80, penthouse25 3.15, sonate 1.50, golf-links 8.16. A static export means no custom headers, no redirects and no default image optimisation (Next.js docs), so the images need pre-generated variants.

## Targets the plan sets

Mobile LCP at most 2.5 s on the home page and on a project page (same lab profile), CLS under 0.1, and no page loading more than 1.5 MB of images on first view. Every indexable page also needs a unique title (at most 60 characters), a description of 120 to 160 characters, a self-referencing canonical, Open Graph and Twitter tags, valid JSON-LD and one H1.

## How to measure it again

**Page facts (HTML)** with the tools in [`tools/seo/`](../../tools/seo/README.md), from the repository root:

```bash
python3 tools/seo/fetch_pages.py tools/seo/data/pages/own \
  https://numaliving.us/ https://numaliving.us/about/ https://numaliving.us/capabilities/ \
  https://numaliving.us/contact/ https://numaliving.us/process/ https://numaliving.us/projects/ \
  https://numaliving.us/projects/golf-links/ https://numaliving.us/login/
python3 tools/seo/audit_pages.py tools/seo/data/pages/own/*.html
python3 tools/seo/audit_pages.py --table tools/seo/data/pages/own
```

`fetch_pages.py` names each saved page after its address (`numaliving.us_index.html` for the home page, `numaliving.us_about.html` for `/about/`). The table shows, per page: status, title and description length, H1 and H2 counts, main-content words, images, images without alt text, whether a canonical exists, the number of Open Graph tags and the JSON-LD types. The fields in each `<name>.analysis.json` are `title`, `description`, `canonical`, `og`, `jsonld_types`, `words_main`, `images`, `images_alt_missing`, `images_alt_empty`, `images_with_size`, `image_exts`, `redirects` and `headers` (cache and `x-robots-tag`). `fetch_pages.py` also keeps the redirect hops and headers in `<name>.meta.json`, which covers the redirect and cache-control lines above. The sitemap and robots.txt are checked by status: `curl -s -o /dev/null -w '%{http_code}\n' https://numaliving.us/sitemap.xml` answered 404 at the baseline, and `curl -s https://numaliving.us/robots.txt` shows whether a `Sitemap:` line exists.

Word counts from the new tool come from the rebuilt text lines, so they can differ by a few words from the first prototype's counts in the table above. Compare later runs with a run of the same tool, not with the figures above, and keep the first run as the tool's own baseline. Run the tool with the same Python release each time: `html.parser` handles broken markup differently from one release to the next (unterminated comments, tags inside `<title>`, odd link addresses), so counts for a malformed page can differ between interpreters, while well-formed pages give the same numbers everywhere (see the Python version note in the [tools README](../../tools/seo/README.md)). Reading the saved prototype analysis files with `audit_pages.py --table` reproduces the figures above.

**Sitemap and search results** once the site is public: `python3 tools/seo/sitemap_report.py https://numaliving.us/sitemap.xml`, then Search Console. For the live crawl of every page at four widths: `python3.14 tools/site-qa/site_check.py --base-url https://numaliving.us/ --expect-https` (it uses the single CloakBrowser seat).

**Speed** with Chrome DevTools, the same profile as above:

1. Open the page in a fresh Chrome window and open DevTools. Turn on the device toolbar and set the width to 390 px.
2. In the Performance panel, set the network to Slow 4G and the CPU to 4x slowdown, and tick "Disable cache" in the Network panel (cold load).
3. Record a page load (reload and start profiling). The trace reports LCP and CLS, and its insights name the LCP request and the image bytes Chrome thinks are avoidable.
4. In the Network panel, filter on Img and add up the transferred bytes per page.
5. Repeat for the home page and for `/projects/golf-links/`, then compare with section 2.

Record the date, the Chrome version and the profile with each new measurement, because lab numbers move with them.
